# 1단계 brief — 마케팅

공통 규칙: `docs/upgrade/briefs/00-common.md` 를 먼저 읽습니다.

## 목표

처음 온 사람이 **링크를 눌러 한 판 하고, 친구에게 보내고 싶게** 만드는 데 무엇이 부족한지 진단하고 고칠 안을 씁니다.
결과물: `docs/upgrade/marketing.md` (근거 그림 · 시안은 `docs/upgrade/marketing/`).

## 할 일

1. **첫인상 점검** — 라이브 링크를 메신저에 붙였을 때(OG 제목 · 설명 · 그림), 브라우저 탭(제목 · 파비콘), 타이틀 화면 첫 3초. 지금 `index.html` 의 meta 와 `public/` 자산을 확인하고 빠진 것을 표로.
2. **포지셔닝** — 한 문장 소개 · 한 줄 훅 후보 3개(한 · 영). 이 게임만의 차별점(오리지널 캐릭터 여섯 · 맵 일곱 · 봇 난이도 · 칩튠 소리 등)을 화면으로 증명되는 것만. 다른 게임 이름은 쓰지 않습니다.
3. **게임 안 문구** — 타이틀 · 선택 화면 · 결과 화면 · 조작 안내 문구를 토스식 해요체로 다듬은 안(지금 문구 → 제안 표). 영어판이 필요한지 의견.
4. **공유 · 재방문 장치** — 결과 화면 공유(결과 카드 그림 · 링크), 기록 · 연승, 「친구와 같은 맵」 링크 같은 장치 후보. 각각 효과 · 비용 · 개인정보 영향(서버 없음 전제 — 지금 정적 배포).
5. **스토어 자료 계획** — 대표 그림(허브 카드 · OG 1200×630), 스크린샷 넷, 짧은 영상 둘의 장면 목록. 촬영 가능한 장면은 직접 찍어 `docs/upgrade/marketing/` 에 1280px 이하로 남깁니다.
6. **허브 연결** — FEYS 다락 오락실 카드의 후크 · 소개(`~/sonix/toy/game-hub/src/data/games.ts` 의 water-balloon-arcade, **읽기만**)가 게임과 맞는지, 고칠 문구 제안.
7. **이름 · 브랜드 위험** — README 첫 줄의 기존 게임 지칭이 공개 표면(레포 공개 여부 · 라이브 · 허브)에 남는지 확인하고 대체 표현 제안.

## 하지 않는 것

코드 · 문서 수정(제안만), 기획 로드맵(기획 팀원 몫 — 마케팅 관점의 기능 요청은 「기획에 넘길 것」 절에).
